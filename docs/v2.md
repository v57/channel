# Channel wire v2

Additions to the `channel` protocol and its libraries: structured errors, subscriptions with dynamic topics,
middleware, server listen options, client request options and connection handling. The TypeScript library in this repo
is the reference; other ports follow it and are checked against the interop fixture (`tests/server.ts`).

## Rules

- **Additive only.** Every v1 message stays valid. A v1 peer ignores the new fields; a v2 peer works with a v1 peer.
- **Source compatible.** Existing public APIs keep compiling. New things are overloads or optional parameters.
- **No speed regressions.** With no middleware and no new options, the process benchmark (`../benchmark`, `bun . ts`)
  stays within 5%.

## 1. Structured errors

Error replies (post responses, stream error events, subscription error responses) may carry two more fields:

```jsonc
{ "id": 4, "error": "banned", "code": 403, "info": { "remaining": 3600 } }
```

- `error`: a non-empty string, the message. Unchanged, so v1 clients keep working.
- `code`: optional, a string or an integer.
- `info`: optional, any JSON.

**Server conversion of a thrown value `e`** (`errorResponse(id, e)` in `channel.ts`):
- string: `error = e`
- object with a string `message` (including `Error` and `ChannelError`): `error = e.message`, plus `code = e.code` (when
  it is a string or an integer) and `info = e.info` when they are defined
- anything else: `error = String(e)`
- an empty result becomes `"error"`

Rethrowing a `ChannelError` from a handler passes its code and info on, so proxies keep them.

**Library codes**, produced by the library itself:

| code | when | `error` text |
|---|---|---|
| `not_found` | no handler for the path or subscription | `api not found` / `subscription not found` |
| `cancelled` | the server-side task was cancelled | `cancelled` |
| `rate_limited` | the `rateLimit` middleware refused the call, `info: { retryAfter: seconds }` | `rate limited` |
| `timeout` | client only, never on the wire: no response in time | `timeout` |
| `disconnected` | client only: the connection dropped and the request can't be replayed, or `stop()` was called | `disconnected` |

Applications use any other codes, for example HTTP-like numbers (401, 403, 404, 500).

**Client API:** requests reject with `ChannelError extends Error { message, code?, info? }`. `String(error)` and
`` `${error}` `` are the message, like the plain string errors of v1. Code that compared the rejection itself with a
string (`error === 'unauthorized'`) compares `error.message` or `String(error)` now.

```ts
import { Channel, ChannelError } from 'channel/client'
try {
  await client.send('v2/error')
} catch (error) {
  if (error instanceof ChannelError && error.code === 403) console.log(error.message, error.info)
}
```

## 2. Subscriptions with dynamic topics

Wire, mostly unchanged:
- request `{ id, sub, body?, context? }`
- success `{ id, topic?, body? }`
- event `{ topic, body }`
- unsubscribe `{ unsub: topic }`

New and clarified:
- **One-shot.** A success response **without `topic`** is one-shot: the client delivers `body` (when present) to the
  handler once, and the subscription is done. It is never replayed and needs no unsubscribe.
- **Snapshot.** The success response's `body` is delivered to the event handler as the first event, and only to the
  subscription it answers. After a reconnect the client subscribes again, and the new response's body is delivered
  again as a fresh snapshot. Events published while disconnected are lost; apps that need them keep their own catch-up.
- **Falsy bodies.** Events and snapshots are delivered whenever the message has a `body` key, including `0`, `false`,
  `""` and `null`. Only a missing `body` means no event. Publishing too: only `undefined` is skipped.

**Server API:**

```ts
// The handler decides the topic from the body and the connection state; throwing refuses the subscription.
channel.sub('chat/list', async ({ body, state, sender, context, path }) => {
  if (!state.userId) throw { message: 'authorization required', code: 401 }
  return { topic: `chat/list/${state.userId}`, body: await snapshot(state.userId) } // omit topic for one-shot
})

// Sends the body to every connection subscribed to the topic, across every listen() of this Channel.
channel.publish(`chat/list/${userId}`, delta)
```

- The server joins the connection to the topic when the handler returns (Bun `ws.subscribe`). It leaves on `unsub` or
  on disconnect.
- `publish` goes through one function, `channel.publisher(event)`, which by default calls `channel.deliver(event)` to
  send it to every `listen()`. A cluster adapter (Redis, NATS) replaces `publisher` and calls `deliver` with the events
  it receives. None is built in.
- The `events()` / `Subscription` API stays. Its `topic(fn)` and `body(fn)` callbacks get a second, optional argument
  `{ state, sender, context }` (missing when called from `Subscription.send()`).

**Client:** `subscribe(path, body, event, options?)` resolves once the server answered, after the snapshot was
delivered. `cancel()` sends `unsub` when it was the topic's last local subscriber.

## 3. Middleware

```ts
channel.use(async (ctx, next) => {
  const started = performance.now()
  try {
    return await next()
  } finally {
    log(ctx.kind, ctx.path, performance.now() - started)
  }
})
// ctx: { kind: 'post' | 'stream' | 'sub', path, body, context, state, sender }
```

- Middleware runs in registration order before the handler, for every incoming post, stream start and sub. It runs on
  both sides, because Channel is symmetric.
- `next()` resolves to the handler's result: the value for a post, `{ topic, body }` for a sub, and the iterator for a
  stream. Middleware sees only the start of a stream.
- Throwing (before or after `next`) sends an error reply, converted as in §1. A middleware may replace `ctx.body` (and
  `ctx.context`) before calling `next()`, and may return a different result.
- `api not found` / `subscription not found` are checked **before** middleware runs.
- With no middleware registered, dispatch takes the same path as without this feature.
- `merge()` copies routes, not the merged channel's middleware.

**Built-ins** (`channel/middleware`):

```ts
import { logger, rateLimit } from 'channel/middleware'
channel
  .use(logger({ slow: 100 }))
  .use(rateLimit({ key: ctx => ctx.state.userId, limit: 10, window: 1, paths: path => path.startsWith('chat/') }))
```

- `rateLimit({ key, limit, window, paths? })`:
  - `key(ctx) => string | undefined` (no key means no limit); `limit` calls per `window` seconds (a sliding window of
    accepted calls); `paths(path) => boolean` filters which paths count.
  - In memory, per process. It throws `{ message: 'rate limited', code: 'rate_limited', info: { retryAfter } }`, with
    `retryAfter` in whole seconds, rounded up.
- `logger({ log?, slow? })`:
  - One line per call: kind, path, milliseconds, and `ok` or the error code and message:
    `post chat/send 0.4ms ok`, `post v2/rate 0.1ms rate_limited rate limited`.
  - `slow` (ms) only logs calls slower than that. `log` defaults to `console.log`.

## 4. Server listen options

`listen(port | 'host:port', options)`:

| option | default | meaning |
|---|---|---|
| `state` | `{}` | `(headers) => State`, sync or async. Headers include the query parameters and `x-hub-remote-ip`. Throwing (or rejecting) refuses the upgrade with `401`. |
| `path` | any | upgrade only requests whose URL path matches (string, exact match, or `(path) => boolean`); others get `404` |
| `maxPayload` | 16 MiB | largest incoming message in bytes; bigger closes the connection (Bun `maxPayloadLength`) |
| `idleTimeout` | 120 | seconds (Bun) |
| `perMessageDeflate` | false | Bun option |
| `onConnect`, `onDisconnect` | | `({ state, sender, subscriptions }) => void` |

## 5. Client request options

`SendOptions` (`send`, `request`, `values`, `subscribe`) gains `timeout` (seconds) and `replay` (boolean). Connect
options gain `requestTimeout` (the default for every post and subscription, none by default).

```ts
const client = new Channel().connect('wss://example.com', { requestTimeout: 10 })
await client.send('payments/charge', order, { replay: false, timeout: 30 })
```

- **Timeout** applies to posts and to the subscription response, not to stream values. When it fires, the call fails
  with code `timeout`. If the request was already written to the socket, the client also sends `{ cancel: id }`;
  otherwise it is just removed from the queue.
- **Replay** defaults to `true`: unanswered requests are sent again after a reconnect.
  - With `replay: false`, a request already written to the socket when the connection drops fails with `disconnected`
    instead. A request queued while offline (never written) is still sent once the connection opens.
- **Order.** Pending requests are replayed in their original order.
- **Subscriptions** that are still active are sent again on reconnect. Cancelled subscriptions and finished one-shots
  are removed from the replay set. A resubscription the server refuses ends the subscription.
- **`stop()`** fails every pending call (posts, streams, subscription responses) with `disconnected`. Fire-and-forget
  calls that may still be pending at `stop()` need a `.catch()`.

## 6. Client connection

- **Reconnect** backs off from 100 ms, doubling up to 5 s, and each delay is randomised to 50-100%. `reconnectNow()`
  resets the backoff and, when waiting to retry, tries at once; apps call it on network changes and when they come to
  the foreground. It is a no-op while connected or connecting.
- **Liveness:** the client pings every `pingInterval` seconds (default 15; 0 disables). With no pong within 10 s, it
  drops the connection and reconnects. Bun's client WebSocket can ping; browsers can't send ping frames, so there it is
  a no-op and the server's pings keep the connection alive (Bun servers ping by default).
- **Headers** come from `headers()`, sync or async, evaluated before every connection attempt. Bun sends them as
  upgrade headers, browsers as query parameters (the server's `state()` sees both).
- **Connection state:** `disconnected | connecting | connected`.
  ```ts
  const observer = client.onStateChange(state => console.log(state)) // called with the current state first
  observer.cancel()
  client.state // 'connected'
  ```
- **Incoming messages:**
  - A frame that isn't valid JSON closes the connection and reconnects; replayable pending calls survive, `replay:
    false` ones fail with `disconnected`.
  - Binary frames are ignored.
  - The TS client has no incoming size limit of its own (browsers don't offer one); the server side limits with
    `maxPayload`. Ports that can should cap incoming messages at 16 MiB.
- **Refused upgrade:** when Bun's client sees a non-101 response (`401` from `state()`, `404` from `path`), the client
  stops, like `stop()`. Browsers can't see the status and keep retrying.

## 7. Interop fixture (`tests/server.ts`, port 2049)

`bun tests/server.ts` runs it standalone. `CHANNEL_TEST_PORT` picks another port. Ports' tests use exactly these routes:

| kind | path | behaviour |
|---|---|---|
| post | `v2/error` | throws `{ message: 'banned', code: 403, info: { remaining: 5 } }` |
| post | `v2/error/code` | throws `{ message: 'slow down', code: 'rate_limited', info: { retryAfter: 1 } }` |
| post | `v2/never` | never answers |
| post | `v2/drop` | increments a global counter, then closes this connection without answering |
| post | `v2/drops` | returns that counter |
| post | `v2/drops/reset` | sets it to 0 |
| post | `v2/headers` | returns the headers the connection was opened with |
| post | `v2/rate` | rate limited to 2 calls per 1 s per connection |
| sub | `v2/room` | body `{ room }` → `{ topic: 'room/' + room, body: 'joined' }` |
| post | `v2/publish` | body `{ room, body }` → `publish('room/' + room, body)`, returns `null` |
| sub | `v2/once` | → `{ body: 'once' }` (one-shot, no topic) |
| sub | `v2/private` | throws `{ message: 'unauthorized', code: 401 }` unless `auth` set a name; otherwise `{ topic: 'private/' + name, body: name }` |

Test cases every library covers (TS: `tests/v2.test.ts`, `tests/client.v2.test.ts`, `tests/middleware.test.ts`):
1. Structured error: message, code (int and string), and info come through.
2. A v1-style string error still works, and so does `api not found` → code `not_found`.
3. One-shot sub: one delivery, no replay after a reconnect.
4. Room sub: snapshot first, then published events. A falsy publish (`0`) is delivered. After unsubscribing, events
   stop, and a reconnect doesn't resubscribe.
5. Reconnect: an active sub is resubscribed and gets a new snapshot.
6. Timeout on `v2/never`, with `{cancel}` sent.
7. `replay: false` on `v2/drop` fails with `disconnected`, and `v2/drops` is 1. With default replay, the counter keeps
   climbing, since every reconnect sends it again (the test stops after 2 drops).
8. Rate limit: the 3rd call fails with `rate_limited` and `info.retryAfter`.
9. Async headers reach `v2/headers` and are re-evaluated on reconnect.
10. `stop()` fails pending calls with `disconnected`.
